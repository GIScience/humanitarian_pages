Maintainer's guide · oqapi-country-reports-vue

ohsome Country Quality Report Internals

This is a ground-up walkthrough of the Vue 3 app behind HeiGIT's OSM data-quality country reports. It covers how the app boots, where the data actually comes from, how the state is organized, and how to change any of it without breaking something else. Read it once and you should be able to open this repository cold and start making real changes.

01 Start here

This project is the frontend half of a two-repository system. A separate Python pipeline, built on Dagster, computes OpenStreetMap data-quality indicators for countries and administrative regions, calling HeiGIT's ohsome-quality-api and ohsome-api along the way. That pipeline isn't covered in this guide; it's a different codebase with a different job. Its only output is files, uploaded to a public S3-compatible bucket. This repository, oqapi-country-reports-vue, is a single-page Vue 3 app that reads those files directly in the visitor's browser and turns them into an interactive dashboard: a map, some charts, a stack of indicator cards.

There's no backend server for this app at runtime. No API keys, no database, no Node process keeping anything alive. Once built, it's just a folder of static HTML, JS and CSS files that could be hosted anywhere, and today that's GitHub Pages. Every number and shape on screen was fetched, at that moment, from a public URL on hot.storage.heigit.org and parsed in the browser, either as a vector tile for the map or as a small analytical database file for everything else. That one fact, that this is a fully static site whose "backend" is a pile of files on S3, explains most of the unusual choices in this codebase. Most notably: an in-browser SQL engine (DuckDB-WASM) standing in for a normal REST API.

The one-sentence mental model

Pick a country and a topic. The app builds a handful of S3 URLs, downloads a vector-tile file for the shapes and one or two small analytical files for the numbers, queries those files with SQL entirely client-side, and draws a map, some gauges and some charts from whatever comes back. Everything else in this guide fills in the detail behind that one sentence.

02 Before you touch anything

Three things in this codebase will actively mislead you if you don't know about them first. Read this section before you edit a single line. It will save you real time.

There are two Vite config files, and the wrong one wins

The project root has both vite.config.ts (the file a human actually maintains) and a stray vite.config.js plus vite.config.d.ts: leftover compiled output from a tsc build that got run once, by accident, and then committed to git. Vite's config search checks vite.config.js before vite.config.ts, so the stale .js file is what actually runs, for both vite dev and vite build. I confirmed this directly: a marker statement dropped into vite.config.js fires; the .ts file never loads at all.

Today the two files hold the same logic, so nothing is actually broken by this. But if you edit vite.config.ts expecting a change to take effect, a new plugin, a new alias, a proxy rule, it silently won't. Fix this the first time you need to touch Vite config: delete vite.config.js and vite.config.d.ts, keep only the .ts file, and drop the now-pointless tsconfig.node.json reference that was compiling it in the first place. Exact steps are in Recipes.

The country list is a hand-maintained candidate list, not a bucket listing

onMounted() in src/views/MainView.vue calls fetchAvailableCountries() for real, no shortcuts. What's worth knowing is how that function decides what's available. It doesn't ask S3 which countries exist, that would need a ListBucket call against the bucket root, and that's still blocked by a bucket-policy issue on the infrastructure side. Instead, src/config/countries.ts exports a plain array, CANDIDATE_COUNTRIES, today ["DEU", "KEN", "NPL"]. fetchAvailableCountries() sends a cheap HEAD request at each candidate's boundaries file and keeps only the ones that actually respond, so listing a country a little early, before its data has finished processing, is harmless. It just won't show up until the file exists.

This means adding a new country to the dropdown is a two-part job, and it's easy to do only half of it: the pipeline has to actually upload that country's files to S3, and its code has to be added to CANDIDATE_COUNTRIES. Forget the second part and a fully-processed country will just never appear, with nothing in the UI telling you why. See the recipe in §13.

A second, visually different layout used to live in this same file

Until recently, MainView.vue rendered either the modern dashboard or a much older "iframe-2col" layout (a fixed two-tile grid used by HeiGIT's HDX platform), depending on how the page was loaded, as two independent code paths sharing one component. That legacy branch has since been removed: the embed case is now the exact same layout in a more compact CSS mode, not a different template. Section 6 covers what's left of that history and what replaced it. If you find a stale reference to "Split View", "iframe-2col", or ReportHeader.vue somewhere, a comment, an old branch name, this document, treat the current source code as correct and flag the reference as outdated.

There is no test suite

There are no unit tests, no component tests, no end-to-end tests. The only automated safety net is TypeScript itself, through vue-tsc, wired into npm run build. In practice that means your review process is: run npx vue-tsc --noEmit -p tsconfig.json to catch type errors, then actually open the app and click through what changed. Don't skip the second part. A type checker has no opinion on whether a map legend is misaligned or a chart failed to render.

04 Running it locally

Three npm scripts, defined in package.json:

CommandWhat it does
npm run devStarts the Vite dev server with hot-reload. Sets VITE_BASE_URL=/ inline so the app runs at the site root locally, instead of the /osm-quality-country-reports/ sub-path GitHub Pages needs (see §12).
npm run buildRuns vue-tsc -b (type-checks everything, fails the build on type errors) and then vite build, emitting static files to dist/.
npm run previewServes the built dist/ folder locally, so you can sanity-check a production build before pushing.

There's no .env file anywhere in this project, and none is needed. The only environment variable in play is VITE_BASE_URL, and it's set inline in the dev script itself rather than read from a dotfile. Everything else the app needs, country data, map tiles, is a public URL already baked into helpers.ts. There's nothing to configure.

To get started from a clean checkout:

cd oqapi-country-reports-vue
npm install
npm run dev
# open the printed http://localhost:5173/... URL

The country dropdown will only show whichever countries in CANDIDATE_COUNTRIES actually have data live on S3 right now, today that's Germany, Kenya and Nepal (see §2). If you add a country there yourself and it doesn't show up, that's a missing S3 upload, not a bug in your checkout.

05 How the app boots

Five files, in order, from the moment the page loads to the moment a map shows up:

  1. index.html Just mounts <div id="app"> and hands off to src/main.ts. Nothing here reaches out to a CDN. Fonts, MapLibre's CSS and the pmtiles protocol handler all come from npm packages instead, see the callout right after this list.
  2. src/main.ts Creates the Vue app, creates a Vue Router instance with exactly one route ("/" → MainView.vue), and mounts everything to #app. It also imports assets/main.css globally (every CSS custom property in the app is defined there) and maplibre-gl/dist/maplibre-gl.css from the maplibre-gl package itself, rather than a <link> tag in index.html.
  3. src/App.vue Eleven lines. Its whole template is <router-view />. There's currently no reason for this app to have more than one route, everything lives on one page, so don't expect to find anything else here.
  4. src/views/MainView.vue Vue Router renders this for the "/" path. This one component is the application: all the state, all the data-fetching orchestration, and the entire template. From here on, this guide is really an explanation of how MainView.vue works.
  5. MainView's own onMounted() Detects whether the page is embedded in an iframe, to switch on compact .embed-mode styling (§6), calls fetchAvailableCountries() to build the real country list (§2), wires up hash-based routing so a URL like #/DEU/roads restores a country and topic on load, and starts a ResizeObserver that keeps MapLibre and Plotly canvases sized correctly as their containers change.
Most external assets are self-hosted, but not all - two CDN dependencies remain

Fonts used to come from Google Fonts, and MapLibre's CSS and the pmtiles protocol handler used to load as global <script> tags from a CDN with a window.pmtiles global. All three of those are gone now. src/assets/fonts/ holds the actual woff2 files (Archivo for the removed legacy layout, Lato for everything else), declared through plain @font-face rules at the top of main.css. pmtiles and maplibre-gl are regular npm dependencies now, imported directly (import { PMTiles, Protocol } from "pmtiles"), so there's no window.pmtiles global left to declare or depend on.

Two genuine third-party network dependencies remain, though, and there's no plan to remove either: DuckDB-WASM's own engine bundle, fetched from a jsDelivr CDN at runtime (§7), and the map's basemap style/tiles/glyphs, served from VersaTiles' public tile server at tiles.versatiles.org (generated in-process by the @versatiles/style npm package, see §10's MetricMap.vue entry). Both were deliberate choices, not oversights: a WASM SQL engine and a full basemap vector tileset aren't things this project bundles or self-hosts. The basemap specifically was chosen to match the same VersaTiles style HeiGIT already uses in its Climate Action Navigator and Hazard-Risk-Composer tools, not picked at random. If you're adding a new external asset, font, icon set, script, still think twice before reaching for a CDN link for anything that can be self-hosted or bundled through npm; that's the pattern this codebase otherwise follows.

06 Embed mode: one layout, not two

This app used to render two entirely different UIs from one component: a modern Single View / Split View dashboard, and a separate, older "iframe-2col" layout (a fixed two-tile grid: one tile with a treemap and tag-coverage bars, one tile with a single map and a small comparison plot) used when HeiGIT's HDX platform embedded this app in an <iframe>. That's gone now. There is exactly one template, one set of state, and one layout: a left sidebar (country, layer, topic, indicator selection) beside a map and a plot/treemap box. What used to be a second, structurally different UI is now the same layout with a compact .embed-mode CSS class applied to it, nothing more.

Near the top of onMounted(), the app still detects embedding:

const inIframe = window.self !== window.top;
const hasEmbedParam = new URLSearchParams(window.location.search).has('embed');
const hasIframe2ColParam = new URLSearchParams(window.location.search).has('iframe-2col');
...
isEmbed.value = inIframe || hasEmbedParam || hasIframe2ColParam;

The old ?iframe-2col param, and the isIframe2Col ref it used to set, predate this layout: they used to select the separate two-tile template. Today they're just another way to ask for the same compact styling as ?embed, kept so any link or embed already using that param doesn't break. test-iframe.html in the project root still exists, a bare <iframe> pointed at the dev server, so real-iframe embedding is reachable locally, but it no longer reaches a different code path, only .embed-mode's CSS.

If you find a reference to the old two-mode split

A stale comment, a variable name, someone's memory of how this worked, treat it as historical, not current. isIframe2Col, viewMode, setViewMode, ChipItem/getChipItems, and ReportHeader.vue (§3) are all gone from the codebase; grepping for any of them in src/ returns nothing. What replaced Split View's panels-array-of-two is covered in §8.

07 Where the data comes from

The S3 bucket layout

Boundaries and indicator data live under https://hot.storage.heigit.org/heigit-hdx-public/ohsome-quality-country-reports/, one folder per country code. That path moved at least once already, an earlier version of this app read from a oqapi_hdx/downloads/ prefix on the same bucket, so don't be surprised if you find that old path mentioned in a stale comment, an old screenshot, or someone's memory of how this used to work. The current path is whatever buildUrls(code, layer) in src/utils/helpers.ts actually builds, treat that function as the one source of truth, not this guide.

FileURL patternFormatWhat it's for
Boundaries<CODE>/<CODE>_boundaries.pmtilesPMTiles (vector tiles)The map shapes themselves, one file per country, shared by every grid layer
Indicator data<CODE>/<CODE>_<layer>_long.parquetApache ParquetOne row per region, topic and indicator: the value, its description, its pre-rendered Plotly figure
Tag distribution<CODE>/<CODE>_<layer>_tag_distribution.parquetApache ParquetPre-rendered treemap figures per topic, grouping tag and measure, plus a timestamp column recording when the pipeline computed that run - the country-level file's copy of this column is also where the "Data current as of" readout gets its date, see below

<CODE> is a 3-letter country code (DEU, KEN, NPL, and so on). <layer> is a grid or admin level, adm0, adm1, h3 by default, or a country-specific override (Germany uses BKG's own vg2500_sta / vg2500_lan / vg1000_krs names, see getCountryLayers() in helpers.ts). Not every layer exists for every country yet. checkParquetExists() does a cheap HEAD request before offering a layer as selectable, so picking one that hasn't been processed doesn't just render a blank gray map with no explanation.

countries.yaml lives at a different prefix, on purpose

fetchAvailableCountries() also fetches one more file, purely to turn a country code into a readable display name: countries.yaml, at .../heigit-hdx-public/oqapi_hdx/countries/countries.yaml. That's the old bucket prefix, not the one above, and that's correct, not a leftover bug. When the boundaries/parquet path moved to ohsome-quality-country-reports/, this particular file didn't move with it. Confirm with a direct request before ever "fixing" this path to match the other one; the last time this got checked, the old path was the one that actually resolved.

Performance: a few sequential waterfalls were flattened into parallel loads

A handful of independent network/query steps used to run one after another purely because of the order they were awaited, not because of any real data dependency - each one adding its full round-trip to how long the dashboard felt slow to load or switch:

  • fetchAvailableCountries() used to await the countries.yaml fetch (plus its dynamic js-yaml import) before starting the CANDIDATE_COUNTRIES existence checks above, even though the display-name YAML and the existence checks don't depend on each other. Both now run in one Promise.all - this gates the very first map render, so it shaves a full round-trip off every initial page load.
  • loadPanelTopicData() used to await loadIndicatorCards() and refreshActiveIndicator() in full before even starting loadPanelTreemap(), even though the treemap reads its own (tag-distribution) parquet file and doesn't depend on either. The treemap load now runs in Promise.all alongside that chain - it still has to run after loadIndicatorCards() sets activeIndicatorKey and before refreshActiveIndicator() reads it, which is the one real dependency in that pipeline, see §9.

handleMapLayerChange() already parallelized its equivalent set of calls with Promise.all; loadPanelTopicData() was the one place that hadn't been brought in line with that pattern.

PMTiles: the map shapes

PMTiles packs an entire vector-tile pyramid into one file that supports HTTP range requests, so MapLibre GL can fetch only the tiles it needs for the current view, from one static file, with no tile server involved. MetricMap.vue registers the pmtiles:// protocol once per map instance and adds it as a normal MapLibre vector source. Every region in the tiles carries a stable id (through promoteId: "id"), and that's what lets the app attach a numeric quality value to each shape through setFeatureState() and recolor it without re-fetching or re-parsing the tiles.

Parquet + DuckDB-WASM: everything else

This is the part that looks unfamiliar if you've mostly built apps that call a REST API. There is no API here. Instead:

  1. DuckDB-WASM boots once. initDuckDB() in src/utils/duckdb.ts downloads DuckDB's own WebAssembly engine, from a jsDelivr CDN bundle, spins it up in a Web Worker, and opens one connection. It's memoized as a module-level singleton with retry-on-failure, so every part of the app shares the same running database engine.
  2. A parquet file gets fetched and registered. registerParquetFile(url, db) downloads the raw bytes with fetch() and hands them to DuckDB as an in-memory virtual file (data_<n>.parquet). Registered files stay cached by URL for the rest of the session (parquetFileCache), and two concurrent requests for the same URL share one in-flight fetch (pendingRegistrations) instead of racing each other.
  3. A plain SQL query runs against it. Every function in dataService.ts, loadIndicators, loadIndicatorLookups, loadTagDistribution, and the rest, is a small SELECT ... FROM read_parquet('...') string, run through runQuery(conn, sql).
  4. Results feed Vue state and MapLibre or Plotly directly. There's no normalization layer and no store in between. The query result gets shaped into exactly what the template or a chart library needs, right there in the calling function.
DuckDB-WASM's one hard rule: never run two queries at once

I confirmed this the hard way during development: dispatching two conn.query() calls at the same time against DuckDB-WASM's single shared connection corrupts both. You'll see errors like "No magic bytes found" on a file that's completely fine on its own. runQuery() in duckdb.ts exists specifically to prevent this: every query, from anywhere in the app, funnels through one enqueue() promise chain that runs strictly one operation at a time. If you ever add a new data-loading function, call the query through runQuery(), never conn.query() directly, or you'll reintroduce this bug the moment two things load at once, which happens routinely: switching topic triggers several data-loading functions in parallel via Promise.all.

MAX()/MIN() over a VARCHAR column silently truncates in this DuckDB-WASM build

Confirmed directly: SELECT MAX(timestamp) FROM read_parquet(...) against a column of full ISO-8601 strings like "2026-09-11T13:13:51Z" came back as the string "2026-09-", eight characters, every time. Not an error, no exception, just quietly wrong data that happened to still parse as a (wrong) date. This looks like DuckDB's internal string_t layout (a short inline buffer for strings, a pointer to heap-allocated bytes for longer ones) not getting fully copied when an aggregate result crosses back over the WASM/JS boundary. A plain row projection of the same column, no aggregate function involved, reads correctly, the same as every other varchar field this app already reads. The fix, and the pattern to follow for anything similar: replace SELECT MAX(col) FROM ... with SELECT col FROM ... ORDER BY col DESC LIMIT 1. loadLatestTimestamp() in dataService.ts is the concrete example. Don't reach for MAX()/MIN() on a varchar column in this codebase again without testing the raw string length of what comes back; a numeric column was not tested and may or may not share this bug.

Two more things worth knowing about this file. The pipeline's treemap figures always label values "km" no matter what the actual measure is, so loadTagDistribution quietly rewrites the unit label and rescales the underlying numbers (fixTreemapUnits) for area (into km²) and length (into km) measures. And Plotly sometimes serializes a numeric array as a compact {dtype, bdata} base64 blob instead of a plain array; decodeTreemapValues() decodes that before any of the rescaling can happen.

08 State & the ViewPanel model

There's no Pinia or Vuex store in this app, even though Pinia is the usual choice for a Vue 3 project this size. Historically the reason was structural: Split View showed two independent map/topic/indicator combinations side by side, and modeling those as one plain object per column, rather than two parallel sets of global refs (which is what the old iframe-2col code did, and exactly why that code resisted extension), was the simpler option. Split View is gone (§6), but the shape it left behind is still exactly how the app is structured today: 

interface ViewPanel {
  id: string;                          // always 'a' now - see below
  selectedTopic: string;               // e.g. "roads"
  topicId: number;                     // bumped on every topic change, forces map re-render
  indicators: string[];                // every indicator name for this topic
  mapLayer: string;                    // e.g. "h3", "adm1", "vg1000_krs"
  activeIndicatorKey: string;          // which indicator is currently shown on map+plot
  indicatorCards: IndicatorCard[];     // one card per non-attribute indicator
  attributeOptions: AttributeOption[]; // one entry per attribute-completeness_* indicator
  selectedAttributeIndicator: string;
  mapLookup: Record<string, number>;  // {regionId → value} driving the map's colors
  activePlotAvailable: boolean;
  featureCount: string;
  totalLength: string;
  tile1Label: string;
  schoolSwitchVisible: boolean;        // schools/hospitals only: operator:type vs isced:level toggle
  schoolSubTopic: string;
  selectedGeomId: string | null;       // set when a single region is clicked on the map
}

// One dashboard view (there's no more Split View) - kept as a one-element
// array rather than a lone object so the per-panel functions below
// (loadIndicatorCards, handleRegionClick, etc.) didn't all need their
// panelIdx parameter ripped out for this redesign.
const panels = ref<ViewPanel[]>([createPanel('a', '', 'h3')]);
const mainPanel = computed(() => panels.value[0]);

There is now always exactly one panel. Everything that mutates state still goes through a function that takes a panelIdx: number as its first argument (loadIndicatorCards(panelIdx, topicName), selectIndicatorCard(panelIdx, indicator), handleMapLayerChange(panelIdx, layer)), and every call site in the template and script just passes the literal 0. Read-only helpers called from the template take a panel: ViewPanel object directly (getActiveCard(panel), getMapLookupRange(panel)), and the template reads through the mainPanel computed instead of looping over the array. This is a deliberate "leave the working plumbing alone" choice, not an oversight: rewriting every one of those functions to drop panelIdx entirely would have touched most of the file for a rename with no behavior change. If you're adding something new that only ever needs to reason about "the current view," it's fine to read straight from mainPanel.value and skip the index parameter; you don't need to preserve the pattern for new code, only understand it for the code that already uses it.

selectedGeomId is what makes clicking a single district on the map narrow every box down to that one region instead of the whole country; §9 walks through that flow end to end. Two fields present in an earlier version, tagCoverage and showTagCoverage, are gone: they backed a standalone attribute-completeness bar chart that no longer exists (§10).

Why this instead of Pinia?

Nothing outside MainView.vue needs this state, and there's only ever one panel, so a local ref<ViewPanel[]> plus plain functions stays the simpler option, this project's own guidance favors simple when simple is enough. If a second, genuinely independent view of this same data ever comes back, that's the moment to reach for Pinia, and probably also the moment to finally drop the one-element-array indirection described above.

Indicators the pipeline skipped for a country don't just show as 0%

Reference-dataset comparison indicators, roads-thematic-accuracy, building-comparison, land-cover-thematic-accuracy, only have a match reference for a handful of countries (Germany, currently). For every other country the pipeline still writes a placeholder row, value 0, description exactly "skipped: indicator not available for this country", rather than omitting the row. UNAVAILABLE_MARKER and isUnavailableDescription() in MainView.vue filter that placeholder out of loadIndicatorCards()'s output entirely, so Nepal's sidebar simply never lists Roads Thematic Accuracy rather than showing it stuck at 0%. If a genuinely new "not available" wording ever shows up from the pipeline, it won't match this exact string and will silently render as a real 0% indicator again, worth checking for if a country's sidebar looks wrong.

Some indicators are forced into "non-quality" treatment even though their value is a real percentage

roads-thematic-accuracy and land-cover-thematic-accuracy both store a genuine 0-1 match/agreement ratio, not a raw count, so they don't trip the data-driven isNoQualityDescription() check the way user-activity does. But a match rate against a reference dataset isn't a "good/bad" quality verdict either, so FORCE_NON_QUALITY_INDICATORS (a hardcoded Set of indicator names) pushes them into the same count-badge treatment by product decision: grey circle instead of a colored ring, no red/amber/ green judgment on the map. Their percentage is still shown correctly, not rounded to a bare integer the way a true raw count would be, and the map's color gradient is fixed to a 0-100% range (fixedColorRange, §10) instead of auto-scaling to whatever narrow range the currently visible regions happen to span. Adding a future indicator to this same treatment means adding its name to this one Set, not writing new branching logic.

09 Life of a click: choosing a topic

The clearest way to see how the pieces fit together is to trace one concrete action from start to finish: clicking "Schools" in the sidebar's Topic row.

  1. The click handler fires. The Topic pill's @click calls handlePanelTopicChange(0, 'schools'). The 0 is always 0, see §8.
  2. The panel's topic and id update. panel.selectedTopic = 'schools'; panel.topicId++. <MetricMap> is keyed only on panel.id (always 'a'), not on topicId, so the map instance is not torn down and recreated on a topic change, it stays mounted and just receives topicId as a normal reactive prop. MetricMap.vue's own watch() on that prop calls updateMapData() to rebuild the colored layer in place. Keeping the same instance across a topic change is what lets click-to-select-a-region keep working without resetting every time you pick a different topic.
  3. loadPanelTopicData(0) runs. This is the one pipeline function, and it does, roughly in parallel where it can:
    • loadIndicators(): what indicators exist for "schools"
    • loadIndicatorCards(0, 'schools'): turns each available indicator into a card, its display value, its gauge-ring percentage, its good/warn/bad/neutral level, and, through isNoQualityDescription() and FORCE_NON_QUALITY_INDICATORS, whether it's a raw count or a forced non-quality indicator rather than a graded quality percentage; also filters out indicators the pipeline marked unavailable for this country (§8)
    • refreshActiveIndicator(0, 'schools'): loads the map-coloring lookup and the small detail plot for whichever indicator ends up active
    • loadPanelTreemap(0): the "Tag distribution" treemap for schools' grouping key, operator:type, or isced:level if that sub-toggle is on
    • updates schoolSwitchVisible so the operator/isced toggle only shows up for schools and hospitals
  4. Vue re-renders on its own. None of the above touches the DOM directly. Every one of those calls just assigns new values onto panel.* properties, and Vue's reactivity re-renders whatever template expression reads them: the hero band's headline number, the sidebar's indicator list, the map's :lookup prop, the plot container.
  5. MetricMap.vue reacts to its own prop changes through watch(). A new topicId triggers updateMapData(), which removes and re-adds the fill/outline layers - but, since the fix described below, reuses the underlying pmtiles vector source as long as the country hasn't changed, instead of tearing it down and re-fetching every visible tile from scratch. It does not re-fit the camera to the country's bounds; a lastFittedBoundsKey guard makes sure fitBounds() only fires when the bounds prop itself actually changes, which only happens on a real country switch. A new lookup object patches each shape's feature-state through applyLookupFeatureStates() without a full rebuild, unless it's a count-type indicator, whose color scale depends on the lookup's own min and max (or a fixedColorRange, §10) and has to rebuild regardless.
  6. Plotly draws the plot. loadActiveIndicatorPlot(0) and loadPanelTreemap(0) both end in a Plotly.react(containerId, fig.data, fig.layout, {...}) call against a uniquely-id'd <div> (active-indicator-plot-a, tag-treemap-a). Plotly.react, not Plotly.newPlot, runs everywhere, so re-rendering the same chart with new data updates it instead of tearing the whole thing down and rebuilding it. Both calls are followed by await nextTick() then an explicit Plotly.Plots.resize(containerId), see the callout below for why.
Fixed: some regions could stay grey ("no data") after a topic switch

Before this fix, step 5 above (updateMapData()) unconditionally removed and re-added the pmtiles source on every topic/indicator/layer switch, even though the source is one file covering every grid layer and only actually needs to change on a real country switch. That forced MapLibre to re-fetch and re-parse every visible tile from scratch on each switch - and because that re-parse is async, it could race against step 3's new lookup arriving: the topic-change's updateMapData() ran immediately (using whichever lookup was still bound at that instant, i.e. the previous topic's), wiping the source; the new topic's lookup then arrived and patched feature-state, but if the freshly re-added source's tiles hadn't finished reloading yet, those tiles came up with no matching feature-state once they did load - stuck grey until some later switch's timing happened to land the other way. Confirmed reproducible at the adm1 layer (larger, more numerous tiles than adm0 make the race window wider), matching a real bug report (Venezuela, Hospitals topic). Fixed by only rebuilding the source when the pmtiles URL itself changes (currentSourceUrl tracking in MetricMap.vue); since the source is no longer wiped on every switch, stale feature-state now has to be cleared explicitly instead, which applyLookupFeatureStates() does via removeFeatureState() for exactly the ids that dropped out of the new lookup.

Switching countries (loadCountry()) is the same idea, one level up. Re-derive the available layers and topics, reset the panel to a fresh default topic, and call loadPanelTopicData(0).

Fixed: loadCountry() now guards against overlapping calls

If a user switched country again before the previous loadCountry() call had finished (plausible on a slow connection, since indicator data for one country can still be loading when the next one is selected), both calls used to run concurrently, and whichever finished last simply overwrote the other's results, including panel.mapLayer, which could leave the map layer from country A paired with country B's code in a subsequent query, or a "Data current as of" date from the wrong country. Confirmed reproducible under a throttled connection. Fixed with a request-generation counter (loadCountryGeneration / isCurrent() in loadCountry()): each call captures its own generation number when it starts, and bails out at every subsequent await once a newer call has superseded it, instead of writing stale results over the newer call's state.

Life of a click: selecting Tag Distribution as the active indicator

Tag Distribution sits in the sidebar's indicator list alongside every real quality indicator, styled as a plain count-badge card with a tag icon (icon="tag" on IndicatorGaugeCard) and no number inside it, even though it isn't a quality indicator at all, it's the same treemap the pipeline always computes per topic. Treating it as "just another indicator" instead of a permanently-visible separate box is the more recent design; the mechanics behind it are worth understanding before touching this area.

  1. It's a pinned, synthetic list entry, not a real indicator. getIndicatorStackItems() appends a { type: 'tag-distribution' } entry after every real indicator card (and after the attribute-completeness group), for any topic where getTagGroupingKey() returns a non-empty grouping tag. It never comes from loadIndicators()'s parquet query.
  2. Selecting it sets the same activeIndicatorKey other indicators use, to a reserved string, TAG_DISTRIBUTION_KEY ('tag-distribution'). getActiveCard() special-cases this key at the top and returns a synthesized IndicatorCard (title, the topic's feature count as its display value, isCount: true) instead of looking one up in panel.indicatorCards.
  3. The map colors by each region's own feature count. loadActiveMapLookup() checks for this same key and calls loadFeatureCountLookup() (dataService.ts) instead of loadIndicatorLookups() - a query against the same tag-distribution parquet loadTagDistribution() already reads for the treemap, just SELECT geomID, sum_value ... WHERE measure = 'count' with no geomID filter, so it comes back with every region's own count in one pass rather than the whole-layer sum a single region's row would give. The result feeds panel.mapLookup directly, and because the synthesized Tag Distribution card already carries isCount: true (previous step), it renders through the same auto-scaled blue gradient any other count indicator uses, no change needed in MetricMap.vue itself. This used to just set panel.mapLookup = {} and let every shape fall back to grey - loadFeatureCountLookup() only exists to color it instead.
  4. The plot box swaps content, but both halves stay mounted. The regular per-indicator plot container and the treemap container are both always in the DOM, toggled with v-show, not v-if/v-else. This matters: loadPanelTreemap() runs on every topic/region change regardless of which indicator is active, and needs its target <div> to exist whenever it fires. An earlier version used v-if/v-else here and the treemap render threw ("No DOM element with id 'tag-treemap-a' exists") every time the div wasn't currently mounted, an exception that aborted the function before it reached the lines further down that set featureCount/totalLength/tile1Label, which is why those readouts appeared permanently stuck. If you ever reach for v-if on one of these two plot containers, this is why not to.
Keeping both plot containers mounted created its own follow-on bug

With both containers always in the DOM, the inactive one sits there display: none. The shared ResizeObserver set up in onMounted() watches both permanently now, and calling Plotly.Plots.resize() on a hidden plot throws ("Resize must be passed a displayed plot div element"). The observer callback now checks el.offsetParent !== null (null exactly for a display: none element in this plain-flow layout) before calling resize(). Separately, Plotly can measure a container mid-layout, right after it's v-shown visible, or before the sidebar/main-column flex widths have settled, and lock its SVG to that narrower snapshot; responsive: true only reacts to a later resize event, it doesn't recheck proactively. That's why loadActiveIndicatorPlot() and loadPanelTreemap() both follow their Plotly.react() call with await nextTick() then an explicit Plotly.Plots.resize() against the now-settled DOM, this is what actually fixed charts intermittently rendering into only the left half of their box.

Life of a click: selecting one district on the map

The other click worth tracing is a click directly on a shape in the map, drilling every box in that panel down to just that one region. This entire feature post-dates the redesign that the rest of this guide describes, so it's easy to miss if you're skimming.

  1. MapLibre reports the click. MetricMap.vue's own click handler runs queryRenderedFeatures against the currently active fill layer at the click point. Clicking the region that's already selected clears the selection instead of re-selecting it, so the same click acts as a toggle.
  2. The map emits, it doesn't decide. MetricMap.vue has no idea what "selected" means to the rest of the app. It just emits regionClick with the clicked feature's id, or null on a toggle-off, and separately draws an outline layer for whichever id its own selectedGeomId prop currently holds.
  3. handleRegionClick(panelIdx, geomId) owns the actual state change. It sets panel.selectedGeomId, then reloads loadIndicatorCards, loadActiveIndicatorPlot and loadPanelTreemap for that one panel, each now pointed at the region, not the country.
  4. Every box narrows to that region. The hero band, the indicator cards or chips, the attribute-completeness bars and the tag-distribution treemap all read from the same panel.selectedGeomId, so there's exactly one flag to check if you're adding a new box and want it to respect the current selection too.
  5. A banner makes the scoping obvious. Whenever panel.selectedGeomId is set, a .region-banner appears at the top of the panel with a "← Back to all of {country}" button, so it's never ambiguous whether you're looking at a country-wide number or one district's.
  6. The selection clears itself when it would stop making sense. Switching the map layer (Kreise → Länder, say) resets selectedGeomId to null, because a region id from one layer means nothing in another. Switching country does the same.

10 Components reference

Where the top bar went

There is no header component any more. The brand mark (ohsome quality-api logo plus "ohsome Country Quality Report" title, src/assets/images/ohsome-quality-api_2000px.png, imported like any other module asset) now sits at the top of the sidebar, inline in MainView.vue's own template (.sidebar-brand), directly above the country <select>. See §3.

MetricMap.vue

One MapLibre GL instance, one per page now that Split View is gone. Rebuilding the colored layer is driven entirely by prop watchers, see the walkthrough in §9. A few things worth knowing:

  • Count versus percentage coloring. isCountIndicator switches the fill-color logic from a fixed red/amber/green quality scale to a continuous blue gradient. A raw count like "4,077 active users" has no universal good/bad threshold the way a 0 to 100% score does.
  • The color gradient's range can be fixed instead of auto-scaled. By default, the blue gradient stretches to the current data's own min and max, fine for an open-ended count, but misleading for a forced-non-quality percentage indicator (§8): a 90% match rate would render as the single darkest color just because no visible region happened to score higher. An optional fixedColorRange: [number, number] prop overrides this with an absolute range instead, MainView.vue passes [0, 1] for anything in FORCE_NON_QUALITY_INDICATORS.
  • Hover-tooltip formatting is a separate decision from the color scale. An isCountIndicator value normally displays as a raw number in the hover popup (4,077, not 407700%). But roads-thematic-accuracy and land-cover-thematic-accuracy are isCountIndicator for their color treatment while still storing a real 0-1 ratio underneath, so an extra showAsPercent prop overrides the hover format back to a percentage independently of the color-scale decision. The two props exist separately on purpose; don't assume one implies the other.
  • Re-fitting only happens on a real country change. A lastFittedBoundsKey ref remembers the last bounds the map actually flew to. updateMapData() runs on every topic, indicator and layer change, but only calls fitBounds() when the incoming bounds prop's key differs from that remembered one. Without this guard, picking a new topic re-ran the same fly-to animation for no reason, even though the view didn't need to move.
  • Clicking a shape selects a region. A selectedGeomId prop and a regionClick emit drive the drill-down feature walked through in §9. The component itself just reports clicks and draws the outline for whatever id it's told is selected; it doesn't decide what "selected" means to the rest of the app.
  • The basemap is VersaTiles' "colorful" style, not a hardcoded style URL. BASEMAP_STYLE, a module-level constant built once via colorful({ baseUrl: "https://tiles.versatiles.org" }) from the @versatiles/style npm package, is passed as the map's style option instead of a plain URL string. It used to be a bare string pointing at OpenFreeMap (tiles.openfreemap.org); that was replaced to match the same basemap HeiGIT's other tools already use, see the callout in §5. The style JSON itself is generated in-process, not fetched, only the vector tiles/glyphs/sprites it references are fetched over the network, from tiles.versatiles.org.
  • The map shows attribution now, in the bottom-right corner (the small "i" toggle on narrow widths). attributionControl: { compact: true, customAttribution: '...' } is passed at map creation - it used to be false, showing nothing at all. Reads MapLibre | © OpenStreetMap contributors [| Boundaries: © ...]: customAttribution is a credit for the library itself (goodwill, not a license requirement - MapLibre GL JS is BSD-3-Clause, no on-screen credit obligation) and is always prepended first, before every source-derived attribution the control collects. The basemap's own OpenStreetMap attribution needs no extra code beyond that - it's baked into @versatiles/style's generated source definition already, and covers every country's boundaries too, since all of them except Germany's are themselves OpenStreetMap-derived (this one is a license condition of OSM's ODbL, not just a nicety). Only Germany needs a third, separate credit merged in, since its boundaries come from BKG instead - a boundariesAttribution string prop, undefined for every other country (nothing extra to add on top of the basemap's own OSM credit), set by MainView.vue since it already knows the selected country, and applied by MetricMap.vue as the boundaries vector source's own attribution field when adding it. Add a new per-country boundary source that isn't OSM-derived and this is the one place that needs updating to credit it correctly.
The map needs an explicit height, not just min-height

MetricMap.vue's root element fills its container with inline height: 100%. A percentage height only resolves against an ancestor whose own height is definite. .mappanel/.map-stage in MainView.vue used to declare only min-height, which still produces a correctly-sized box visually (the flex/content-driven layout genuinely renders at the right size), but leaves every ancestor's declared height as auto. A descendant's height: 100% doesn't resolve against an "auto" ancestor, it collapses to 0, confirmed directly: the map's container div measured 0px tall via getBoundingClientRect() even though its parent measured the expected ~520px. The fix was switching .mappanel to an explicit height (not min-height), which gives the whole percentage chain a real, definite size to resolve against. If a future layout change ever makes the map (or anything else relying on height: 100% to fill its box) render blank again, check for exactly this: a min-height-only ancestor somewhere up the chain.

IndicatorGaugeCard.vue & AttributeCompletenessCard.vue

The sidebar's indicator list. IndicatorGaugeCard shows one indicator as a gauge ring, or, for a count-type indicator (level === 'neutral'), a plain badge instead of a ring, a percentage ring would imply a graded score that a raw count doesn't have. That badge's icon is now configurable through an icon prop: 'people' (default, used for genuine counts like User Activity) shows a small people icon plus the count; 'tag' (used for the Tag Distribution entry, §9) shows a plain tag icon with no number at all, since Tag Distribution isn't a count of anything in the sense the number would suggest. AttributeCompletenessCard is the same card shape but bundles a <select>, so one card can represent several attribute-completeness indicators, surface, maxspeed, name, switching which one shows without needing a separate card per attribute.

Neither component owns a description or a fold/expand toggle any more. Both used to: each card had its own expanded ref and a chevron button that faded a description paragraph in and out. That's gone, the active indicator's description now renders once, centrally, in the plot box's right-hand column (.plotpanel-desc, §11), not duplicated per card. If you're adding a new card type, don't reintroduce a per-card description, wire its text into getActiveCard()'s returned description field instead so it shows up in that one shared place.

The standalone "Attribute completeness" bar-chart box is gone

An earlier version had a separate, always-visible box below the indicator list showing every attribute-completeness_* indicator as a horizontal bar, in addition to the single value AttributeCompletenessCard's own dropdown showed. That box was removed as redundant; the dropdown card is the only place attribute- completeness values show now. panel.tagCoverage and panel.showTagCoverage, which fed it, are gone from ViewPanel too (§8), and loadTagCoverage() in dataService.ts is now dead code as a result (§7).

ReportFooter.vue

Static legal links (Contact, Privacy, Imprint) and the ohsome dashboard badge. No props, no state. Safe to edit freely.

There's exactly one palette. No dark mode toggle exists in this app today.

--font-sans, --color-bg, --color-card-bg, --color-text, --border-radius and --font-size-text, near the top of main.css, existed to keep the old iframe-2col layout rendering in its own Archivo-based style. A few visual patterns repeat across the current UI, and it helps to know them by name.

The pill is a bordered, rounded button that turns solid --accent when active. It shows up for topic selection and layer selection in the sidebar, both defined in MainView.vue's own scoped <style> (.topic-pills-row .pill, .layer-switch button). If you add a new pill-style control elsewhere and it looks unstyled, remember Vue's <style scoped> doesn't share CSS between components even when the class name matches, the component rendering it needs its own copy of the rule.

The sidebar (.sidebar) is the app's left column: the brand block, then a labeled section each for country, layer, topic and indicator selection (.sidebar-section, .sidebar-label). The hero band (.band) is the large "Medium 61%"-style headline box at the top of the main column, next to the plain readouts row (.readouts), summarizing whichever indicator is currently active. The active indicator's description used to render inside this band; it was moved out into the plot box instead (next paragraph), so .band today is just the label/level/percentage, nothing else.

The plot box's description column (.plotpanel-desc) is a roughly 1/3-width column to the right of the chart or treemap (.plotpanel-main, 2/3 width, both inside .plotpanel-layout), separated by a vertical divider, holding the active indicator's description text under an "About this indicator" label. This is a deliberate, requested placement, not an arbitrary one, it replaced an earlier version that put the same text inside the hero band, and an even earlier one that put it inside each sidebar card's fold-out (§10). If this moves again, getActiveCard(panel)?.description is the one place that feeds all of them; only the template markup around it needs to change.

Tailwind: present, but mostly unused

Tailwind is installed and configured (tailwind.config.js, postcss.config.js), and its @tailwind directives sit at the top of main.css. In practice, almost none of the UI actually uses Tailwind utility classes. The design system above, hand-written CSS custom properties plus scoped <style> blocks, is what you'll be editing most of the time. Tailwind is effectively legacy plumbing at this point. Use its utility classes for something new if you want to, but don't expect much precedent for it in the existing code.

12 Build, deploy & hosting

Deployment is fully automated through .github/workflows/deploy.yml at the repository root, one level above this Vue project, since this repo also holds the separate Python pipeline: 

on:
  push:
    branches: [main]

jobs:
  build-and-deploy:
    steps:
      - checkout
      - cd oqapi-country-reports-vue && npm install && npm run build
      - deploy ./oqapi-country-reports-vue/dist to the gh-pages branch

In other words: every push to main rebuilds and redeploys the live site automatically, with no manual step and no staging environment. Test locally before merging to main. There's no safety net after that point besides GitHub Pages' own rollback, which just means redeploying an older commit by hand.

The built app is served at https://<org>.github.io/osm-quality-country-reports/, note the sub-path. That's why vite.config.ts/.js hardcode base: '/osm-quality-country-reports/' as the default, overridden to / only for local dev through the VITE_BASE_URL env var in the dev script. If this app ever moves to a different host or a custom domain, this base path is the first thing to change. Get it wrong and every asset URL in the built dist/ output 404s.

13 Recipes: common changes

Concrete steps for the changes you're most likely to want to make.

Fix the duplicate Vite config problem
  1. Delete vite.config.js and vite.config.d.ts.
  2. In tsconfig.json, remove the "references": [{ "path": "./tsconfig.node.json" }] line. That's what caused vite.config.ts to get compiled into .js in the first place, through vue-tsc -b's project-reference build.
  3. Delete tsconfig.node.json itself, now unused.
  4. Run npm run build once to confirm nothing else depended on it, then run npm run dev and confirm the app still starts.

Worth checking after you do this: vite.config.js has been seen regenerating itself with a newer timestamp than the .ts file it's supposed to be a stale copy of, which points at some other build step still running tsc against the project root. Track that down before assuming this fix stuck.

Add a country to the picker
  1. Confirm the pipeline has actually uploaded that country's files: at minimum <CODE>/<CODE>_boundaries.pmtiles under the S3 path in §7. A quick curl -I against that URL is enough.
  2. Add the 3-letter code to CANDIDATE_COUNTRIES in src/config/countries.ts.
  3. Check countries.yaml knows a display name for the code; if not, add an entry to the countryExceptions map in fetchAvailableCountries() (dataService.ts) instead of waiting on that file to be updated.
  4. Reload the app and confirm the country appears and actually loads data. It's also the only real way to notice whether Germany's special-cased BKG layer names in getCountryLayers() have quietly leaked into code paths that were supposed to be country-agnostic.
Change the map's quality color scale
  1. The colors live in three places that have to stay in sync, by hand - none of them read from a shared source: buildFillColorExpression() in MetricMap.vue (the actual MapLibre paint expression, currently #D55E00 / #F0E442 / #009E73), every .map-legend block in MainView.vue's template (the on-screen key, hardcoded inline as style="background:#D55E00" and so on - MapLibre paint expressions and inline template styles can't read CSS custom properties, which is why these two can't just reference the token below), and the --good / --warn / --bad design tokens in main.css (used by the indicator gauge rings and the hero band's left border). Change one without the other two and the map will visibly disagree with the cards describing the same data.
  2. If you're instead changing a count-style indicator's gradient (the blue scale), remember there are two separate range behaviors: auto-scaled to the current data's own min/max by default, or a fixed fixedColorRange for anything in FORCE_NON_QUALITY_INDICATORS (§8, §10). Match the legend caps (getLegendCapText()) to whichever one the map is actually using, they read the same flag.
Mark an indicator as "non-quality" without a matching data-driven marker
  1. Confirm first, with a real query against the parquet, whether the indicator's own description already contains the exact marker isNoQualityDescription() checks for. If it does, you don't need this recipe, it'll already get count-badge treatment for free.
  2. If not, and it's still not a "good/bad" quality verdict (a match rate against a reference dataset, say), add its indicator name to FORCE_NON_QUALITY_INDICATORS in MainView.vue (§8).
  3. Check whether the indicator's underlying value is a genuine 0-1 ratio (most likely) or an actual raw count. If it's a ratio, its displayValue must stay computed off isRawCount, not isCount, in loadIndicatorCards(), or it'll round to a bare, wrong integer instead of showing a percentage. See the callout in §8 for exactly this mistake.
  4. Test it in a real browser against a country where the indicator actually has data, not just one where it's unavailable (next recipe), the 0%/unavailable case can't tell you whether the percentage formatting is right.
Hide an indicator that's unavailable for some countries
  1. Query the parquet directly for a country where the pipeline doesn't compute this indicator, and check the exact wording of its placeholder description. If it matches UNAVAILABLE_MARKER in MainView.vue already ("skipped: indicator not available for this country"), nothing else to do, isUnavailableDescription() already filters it out of loadIndicatorCards()'s output (§8).
  2. If the pipeline uses different wording for this case, either normalize it upstream, or extend the check here, but confirm the new wording is stable and topic-agnostic before matching on it.
Add a brand-new topic-specific config (like schools/hospitals have)
  1. Add an entry to topicConfig in helpers.ts only if you need a preferred default attribute-completeness indicator for the topic, that's its one remaining use, inside loadIndicatorCards(). It's no longer read by anything else.
  2. If the new topic needs its own tag-distribution grouping key, add a branch to getTagGroupingKey() in the same file.
  3. Most topics don't need topic-specific code at all beyond that. loadIndicatorCards already works generically off whatever indicators the parquet file actually contains for that topic. Special-case only genuinely special behavior, like the schools/hospitals operator-type / isced-level sub-toggle. Search for schoolSwitchVisible to see everywhere that toggle reaches.
Add a second real page/route
  1. Create a new file under src/views/, say AboutView.vue.
  2. In src/main.ts, add a second entry to the routes array passed to createRouter(): { path: '/about', component: AboutView }.
  3. Nothing else needs to change. App.vue's <router-view /> already renders whatever route matches.
  4. GitHub Pages serves this as a static site with one entry point, so a hard refresh on /about directly can 404 without an SPA-fallback trick (a duplicated 404.html). Worth testing once real deep-linkable routes exist.

14 Known rough edges

A punch list, in one place. Nothing here is broken today, but all of it is worth knowing before you assume the surrounding code behaves normally.

  • Two Vite config files, wrong one active. Still physically present (confirmed both vite.config.js and vite.config.ts exist at the project root, most recently touched at the same timestamp). §2 and the first recipe above.
  • Country list needs manual maintenance. Adding a country means editing CANDIDATE_COUNTRIES by hand, because the S3 ListBucket permission this could otherwise be automated with is still blocked. §2.
  • No automated tests of any kind. Type-checking (vue-tsc) is the only automated gate; manual browser verification is mandatory for every change.
  • No ESLint or Prettier configuration. Code style is whatever the existing file already looks like. Match it by hand.
  • MAX()/MIN() over a varchar column silently truncates in the current DuckDB-WASM build. Confirmed directly, cost real debugging time before the root cause was found. Use ORDER BY ... LIMIT 1 instead. §7.
  • Several design tokens in main.css are now fully dead (--font-sans, --color-bg, --color-card-bg, --color-text, --border-radius, --font-size-text), left over from the removed iframe-2col layout. Safe to delete, just grep first. §11.
  • loadTagCoverage() in dataService.ts is exported but has zero call sites, left over from a removed attribute-completeness bar chart. Safe to delete. §7, §10.
  • MainView.vue is a single file, around 1,400 lines. There's no enforced component boundary between sidebar controls, the hero band, indicator picking, the region drill-down, and so on. If this file keeps growing, pulling some of that out into dedicated components, the way MetricMap.vue and the two indicator card components already are, is a reasonable next step. It's noticeably smaller than it used to be (it briefly exceeded 2,800 lines before the Split View and iframe-2col removal), so this is less urgent than it once was.
  • Tailwind is installed but mostly dead weight. §11. Not harmful, just don't expect to find conventions for using it.
  • Every parquet file is fetched as a whole file into memory (registerParquetFile(), §7) rather than queried in place over HTTP range requests, even when a query only touches one topic/indicator. Worth investigating whether DuckDB-WASM's native remote-parquet reading could cut bytes transferred for the larger grid-layer files, once hot.storage.heigit.org's range-request/CORS support is confirmed. Not started.
  • Every DuckDB-WASM query, across every card/plot/treemap, is serialized through one shared connection and one operation queue (enqueue() in duckdb.ts, §7) - safe (this is what fixes the "No magic bytes found" corruption), but means queries never actually run concurrently even when they're unrelated. Opening a second connection for independent query sets might allow real parallelism, but needs a deliberate concurrency-safety test first, not just a config flip. Not started.

15 Glossary

Topic
A category of OSM features this app reports on: roads, buildings, land cover, schools, hospitals. Each topic has its own set of relevant indicators.
Indicator
One specific quality metric within a topic, currentness, mapping-saturation, attribute-completeness_surface, and so on. Computed upstream by the ohsome-quality-api pipeline, not by this app.
Layer / grid layer
The geographic granularity a map currently shows: a whole country (adm0), a state or region (adm1), or a hexagonal grid (h3). Chosen per panel through the "Layer" pill row.
Grouping key / grouping tag
The OSM tag a topic's "Tag distribution" treemap breaks down by: highway for roads, building for buildings, operator:type for schools/hospitals by default.
PMTiles
A single-file vector-tile format that supports HTTP range requests, so a map can be served from one static file with no tile server. See §7.
Parquet
A compact, columnar binary file format for tabular data. This app treats every parquet file as a small queryable database through DuckDB-WASM, instead of parsing it into JSON up front.
DuckDB-WASM
A full SQL database engine compiled to WebAssembly, running entirely in the visitor's browser inside a Web Worker. It lets this app run real SQL queries against remote parquet files with no server-side query API. See §7.
ohsome-quality-api / ohsome-api
HeiGIT's separate backend services, not part of this repository, that the Dagster pipeline calls to actually compute quality indicators from OpenStreetMap history data. This app only ever reads their pre-computed output files from S3.
Panel
The one active map/topic/indicator combination, modeled as a single-element array of ViewPanel (a shape left over from a removed two-panel Split View, see §8), exposed to the template as mainPanel.
Embed mode
A compact CSS styling mode (.embed-mode, isEmbed), applied to the same single layout when the page is embedded in an <iframe> or loaded with ?embed/?iframe-2col. Used to be a structurally different template; no longer is. See §6.
Non-quality indicator
An indicator shown as a plain count-style badge instead of a graded quality ring, because its number isn't a "good/bad" verdict: a genuine raw count (user-activity), or a match/agreement rate forced into the same treatment by product decision (roads-thematic-accuracy, land-cover-thematic-accuracy, via FORCE_NON_QUALITY_INDICATORS). See §8.
Hero band
The large "Medium 61%"-style headline box at the top of the main column, summarizing whichever indicator is currently active. No longer holds the description text, see §11.
Region drill-down
Clicking a single district (or state, or hex cell) on the map to scope every box to just that region. Backed by panel.selectedGeomId. See §9.
Candidate country list
CANDIDATE_COUNTRIES in src/config/countries.ts, the hand-maintained array of country codes the dropdown checks against S3. See §2.

16 Where to go from here

Suggested reading order if you're starting from zero, in one sitting:

  1. Read this whole document once, top to bottom, without touching code.
  2. npm run dev the app and click through a few countries, topics and indicators, including Tag Distribution, for a few minutes, watching the Network tab to see the pmtiles and parquet requests happen live.
  3. Open src/views/MainView.vue side by side with §6 through §9 of this guide and trace one topic switch by hand, matching what you read here to the actual lines.
  4. Check whatever project instructions live in CLAUDE.md at the repo root for house rules on how changes should be made (small, surgical, verified in a real browser). Those apply to this project just as much as to any AI assistant working on it.
  5. Pick one item from §14 and fix it, as practice, before attempting a real feature.

This document describes the codebase as of the sidebar redesign that removed Split View and the legacy iframe-2col layout in favor of one unified template, moved the brand and country/topic/layer/indicator pickers into a left sidebar, folded Tag Distribution into the indicator list instead of a permanently-visible box, moved indicator descriptions into the plot box, added the non-quality-indicator and unavailable-indicator filtering described in §8, and switched "Data current as of" to the parquet's own timestamp. It will drift out of date again as the app keeps changing, that's normal, not a sign this guide was written carelessly. Treat it as a map of the territory on the day it was last updated, not a promise about the future. When in doubt, the source code is the final authority. This guide's only job is to make that source code fast to understand.
