Maintainer's guide · oqapi-country-reports-vue

Quality Atlas Internals

This is a ground-up walkthrough of the Vue 3 app behind HeiGIT's OSM data-quality country reports. It covers how the app boots, where the data actually comes from, how the state is organized, and how to change any of it without breaking something else. Read it once and you should be able to open this repository cold and start making real changes.

01 Start here

This project is the frontend half of a two-repository system. A separate Python pipeline, built on Dagster, computes OpenStreetMap data-quality indicators for countries and administrative regions, calling HeiGIT's ohsome-quality-api and ohsome-api along the way. That pipeline isn't covered in this guide; it's a different codebase with a different job. Its only output is files, uploaded to a public S3-compatible bucket. This repository, oqapi-country-reports-vue, is a single-page Vue 3 app that reads those files directly in the visitor's browser and turns them into an interactive dashboard: a map, some charts, a stack of indicator cards.

There's no backend server for this app at runtime. No API keys, no database, no Node process keeping anything alive. Once built, it's just a folder of static HTML, JS and CSS files that could be hosted anywhere, and today that's GitHub Pages. Every number and shape on screen was fetched, at that moment, from a public URL on hot.storage.heigit.org and parsed in the browser, either as a vector tile for the map or as a small analytical database file for everything else. That one fact, that this is a fully static site whose "backend" is a pile of files on S3, explains most of the unusual choices in this codebase. Most notably: an in-browser SQL engine (DuckDB-WASM) standing in for a normal REST API.

The one-sentence mental model

Pick a country and a topic. The app builds a handful of S3 URLs, downloads a vector-tile file for the shapes and one or two small analytical files for the numbers, queries those files with SQL entirely client-side, and draws a map, some gauges and some charts from whatever comes back. Everything else in this guide fills in the detail behind that one sentence.

02 Before you touch anything

Three things in this codebase will actively mislead you if you don't know about them first. Read this section before you edit a single line. It will save you real time.

There are two Vite config files, and the wrong one wins

The project root has both vite.config.ts (the file a human actually maintains) and a stray vite.config.js plus vite.config.d.ts: leftover compiled output from a tsc build that got run once, by accident, and then committed to git. Vite's config search checks vite.config.js before vite.config.ts, so the stale .js file is what actually runs, for both vite dev and vite build. I confirmed this directly: a marker statement dropped into vite.config.js fires; the .ts file never loads at all.

Today the two files hold the same logic, so nothing is actually broken by this. But if you edit vite.config.ts expecting a change to take effect, a new plugin, a new alias, a proxy rule, it silently won't. Fix this the first time you need to touch Vite config: delete vite.config.js and vite.config.d.ts, keep only the .ts file, and drop the now-pointless tsconfig.node.json reference that was compiling it in the first place. Exact steps are in Recipes.

The real country list is switched off

Open src/views/MainView.vue and look inside onMounted(). You'll find this: 

// TEMPORARY local test-only bypass: the S3 ListBucket call this depends on is
// currently 403ing (pre-existing bucket-policy issue, unrelated to the new
// pipeline). Hardcoding DEU here so the dropdown isn't stuck empty while
// testing the new pmtiles/parquet integration. Revert this block once that's
// fixed for real.
countries.value = [{ value: 'DEU', label: 'Germany' }];
selectedCountry.value = 'DEU';
/*
const fetchedCountries = await fetchAvailableCountries();
countries.value = fetchedCountries.map(c => ({ value: c.code, label: c.name }));
...
*/

The real implementation, fetchAvailableCountries() in src/services/dataService.ts, lists the S3 bucket's downloads/ prefix to discover every country that's actually been processed. It's written, it works, and it's simply commented out. Right now the country dropdown shows Germany and nothing else, no matter how many countries have real data sitting on S3. This is almost certainly the first thing worth fixing once the S3 bucket-policy issue behind it (a 403 on the ListBucket call) gets resolved on the infrastructure side. At that point the fix is two lines: delete the hardcoded block, uncomment the real call.

Two completely different UIs live in one file, on purpose

MainView.vue renders either the modern Single View / Split View dashboard, or a much older, visually different "iframe-2col" layout, depending on how the page was loaded. They share one Vue component and a few pieces of state, but otherwise run as two independent code paths inside the same template. Section 6 covers this in full. For now: if you're editing the map or the indicator cards and your change doesn't show up, check which of the two branches you're actually looking at in the browser.

There is no test suite

There are no unit tests, no component tests, no end-to-end tests. The only automated safety net is TypeScript itself, through vue-tsc, wired into npm run build. In practice that means your review process is: run npx vue-tsc --noEmit -p tsconfig.json to catch type errors, then actually open the app and click through what changed. Don't skip the second part. A type checker has no opinion on whether a map legend is misaligned or a chart failed to render.

04 Running it locally

Three npm scripts, defined in package.json:

npm run devStarts the Vite dev server with hot-reload. Sets VITE_BASE_URL=/ inline so the app runs at the site root locally, instead of the /osm-quality-country-reports/ sub-path GitHub Pages needs (see §12).

There's no .env file anywhere in this project, and none is needed. The only environment variable in play is VITE_BASE_URL, and it's set inline in the dev script itself rather than read from a dotfile. Everything else the app needs, country data, map tiles, is a public URL already baked into helpers.ts. There's nothing to configure.

To get started from a clean checkout:

cd oqapi-country-reports-vue
npm install
npm run dev
# open the printed http://localhost:5173/... URL

Before you see anything interesting, remember §2: the country dropdown is hardcoded to Germany only, regardless of what's really on S3. That's expected, not a setup problem on your end.

05 How the app boots

Five files, in order, from the moment the page loads to the moment a map shows up:

  1. index.html Loads two Google font families, the MapLibre GL CSS stylesheet, and pmtiles.js (a small script that teaches MapLibre how to read the .pmtiles vector-tile format) from CDNs, then mounts <div id="app"> and hands off to src/main.ts.
  2. src/main.ts Creates the Vue app, creates a Vue Router instance with exactly one route ("/" → MainView.vue), and mounts everything to #app. It also imports assets/main.css globally; that's where every CSS custom property (design token) in the app gets defined.
  3. src/App.vue Eleven lines. Its whole template is <router-view />. There's currently no reason for this app to have more than one route, everything lives on one page, so don't expect to find anything else here.
  4. src/views/MainView.vue Vue Router renders this for the "/" path. This one component is the application: all the state, all the data-fetching orchestration, and, through v-if/v-else at the top of its template, both possible layouts. From here on, this guide is really an explanation of how MainView.vue works.
  5. MainView's own onMounted() Detects whether the page is embedded in an iframe (§6), sets a hardcoded country (§2), wires up hash-based routing so a URL like #/DEU/roads restores a country and topic on load, and starts a ResizeObserver that keeps MapLibre and Plotly canvases sized correctly as their containers change.

06 The two faces of MainView.vue

Near the top of onMounted(), the app decides which of two entirely different UIs to show: 

const inIframe = window.self !== window.top;
const hasEmbedParam = new URLSearchParams(window.location.search).has('embed');
const hasIframe2ColParam = new URLSearchParams(window.location.search).has('iframe-2col');
...
isEmbed.value = inIframe || hasEmbedParam;
isIframe2Col.value = inIframe || hasIframe2ColParam;

In plain terms: if this page ever loads inside a real <iframe> (from anywhere), or the URL carries ?iframe-2col, isIframe2Col becomes true and stays true for the rest of the session. test-iframe.html in the project root exists purely to trigger this path during local development.

Normal mode currentiframe-2col mode legacy
Who sees itAnyone visiting the site directly (the GitHub Pages URL)HeiGIT's HDX platform, which embeds this app in an <iframe> on their own pages
LayoutSingle View (one map + one stack of gauge cards) or Split View (two independent columns side by side)A fixed two-tile grid: one tile with a treemap + tag-coverage bars, one tile with a single map + a small comparison plot

This split runs all the way down through the template with v-if="!isIframe2Col" / v-else, and through the script with functions that only make sense in one mode. loadPanelTopicData(panelIdx) belongs to Normal mode; loadMapData() and loadTreemap() belong to iframe-2col. Both branches lean on some shared helpers (buildUrls, getTagGroupingKey, the DuckDB query functions), but they don't share UI state.

Why keep two modes in one file at all?

HeiGIT's HDX platform embeds this exact app by URL, and that embed's layout (id="tile5" / id="tile6", specific CSS classes) is a contract with that other system. Rebuilding Single/Split View this year didn't change what HDX embeds, so the old layout was left alone on purpose instead of migrated, and the two now sit side by side in the same file. If you're not working on the HDX embed, treat everything under v-else as off-limits, and everything under v-if="!isIframe2Col" as "the app."

07 Where the data comes from

The S3 bucket layout

Every file this app ever reads lives under one public bucket root: https://hot.storage.heigit.org/heigit-hdx-public/oqapi_hdx/. Two kinds of files matter, and both come from buildUrls(code, layer) in src/utils/helpers.ts:

FileURL patternFormatWhat it's for
Boundariesdownloads/<CODE>/<CODE>_boundaries.pmtilesPMTiles (vector tiles)The map shapes themselves, one file per country, shared by every grid layer
Indicator datadownloads/<CODE>/<CODE>_<layer>_long.parquetApache ParquetOne row per region, topic and indicator: the value, its description, its pre-rendered Plotly figure
Tag distributiondownloads/<CODE>/<CODE>_<layer>_tag_distribution.parquetApache ParquetPre-rendered treemap figures per topic, grouping tag and measure

<CODE> is a 3-letter country code (DEU, RWA, and so on). <layer> is a grid or admin level, adm0, adm1, h3 by default, or a country-specific override (Germany uses BKG's own vg2500_sta / vg2500_lan / vg1000_krs names, see getCountryLayers() in helpers.ts). Not every layer exists for every country yet. checkParquetExists() does a cheap HEAD request before offering a layer as selectable, so picking one that hasn't been processed doesn't just render a blank gray map with no explanation.

PMTiles: the map shapes

PMTiles packs an entire vector-tile pyramid into one file that supports HTTP range requests, so MapLibre GL can fetch only the tiles it needs for the current view, from one static file, with no tile server involved. MetricMap.vue registers the pmtiles:// protocol once per map instance and adds it as a normal MapLibre vector source. Every region in the tiles carries a stable id (through promoteId: "id"), and that's what lets the app attach a numeric quality value to each shape through setFeatureState() and recolor it without re-fetching or re-parsing the tiles.

Parquet + DuckDB-WASM: everything else

This is the part that looks unfamiliar if you've mostly built apps that call a REST API. There is no API here. Instead:

  1. DuckDB-WASM boots once. initDuckDB() in src/utils/duckdb.ts downloads DuckDB's own WebAssembly engine, from a jsDelivr CDN bundle, spins it up in a Web Worker, and opens one connection. It's memoized as a module-level singleton with retry-on-failure, so every part of the app shares the same running database engine.
  2. A parquet file gets fetched and registered. registerParquetFile(url, db) downloads the raw bytes with fetch() and hands them to DuckDB as an in-memory virtual file (data_<n>.parquet). Registered files stay cached by URL for the rest of the session (parquetFileCache), and two concurrent requests for the same URL share one in-flight fetch (pendingRegistrations) instead of racing each other.
  3. A plain SQL query runs against it. Every function in dataService.ts, loadIndicators, loadIndicatorLookups, loadTagDistribution, and the rest, is a small SELECT ... FROM read_parquet('...') string, run through runQuery(conn, sql).
  4. Results feed Vue state and MapLibre or Plotly directly. There's no normalization layer and no store in between. The query result gets shaped into exactly what the template or a chart library needs, right there in the calling function.
DuckDB-WASM's one hard rule: never run two queries at once

I confirmed this the hard way during development: dispatching two conn.query() calls at the same time against DuckDB-WASM's single shared connection corrupts both. You'll see errors like "No magic bytes found" on a file that's completely fine on its own. runQuery() in duckdb.ts exists specifically to prevent this: every query, from anywhere in the app, funnels through one enqueue() promise chain that runs strictly one operation at a time. If you ever add a new data-loading function, call the query through runQuery(), never conn.query() directly, or you'll reintroduce this bug the moment two things load at once. Split View's two columns loading together is exactly that moment.

Two more things worth knowing about this file. The pipeline's treemap figures always label values "km" no matter what the actual measure is, so loadTagDistribution quietly rewrites the unit label and rescales the underlying numbers (fixTreemapUnits) for area (into km²) and length (into km) measures. And Plotly sometimes serializes a numeric array as a compact {dtype, bdata} base64 blob instead of a plain array; decodeTreemapValues() decodes that before any of the rescaling can happen.

08 State & the ViewPanel model

There's no Pinia or Vuex store in this app, even though Pinia is the usual choice for a Vue 3 project this size. The reason is structural. Single View shows one independent map/topic/indicator combination. Split View shows two, side by side, each fully independent of the other. Rather than model that as two parallel sets of global refs, which is exactly what the legacy iframe-2col code does, and exactly why that code resists extension, Normal mode represents each visible column as one plain object: 

interface ViewPanel {
  id: string;                          // 'a' or 'b' - used to build unique DOM ids
  selectedTopic: string;               // e.g. "roads"
  topicId: number;                     // bumped on every topic change, forces map re-render
  indicators: string[];                // every indicator name for this topic
  mapLayer: string;                    // e.g. "h3", "adm1", "vg1000_krs"
  activeIndicatorKey: string;          // which indicator is currently shown on map+plot
  indicatorCards: IndicatorCard[];     // one card per non-attribute indicator
  attributeOptions: AttributeOption[]; // one entry per attribute-completeness_* indicator
  selectedAttributeIndicator: string;
  mapLookup: Record<string, number>;  // {regionId → value} driving the map's colors
  mapAvg: number;
  activePlotAvailable: boolean;
  featureCount: string;
  totalLength: string;
  tile1Label: string;
  tagCoverage: TagCoverageItem[];
  showTagCoverage: boolean;
  schoolSwitchVisible: boolean;        // schools/hospitals only: operator:type vs isced:level toggle
  schoolSubTopic: string;
}

const panels = ref<ViewPanel[]>([...]) holds one or two of these. viewMode ('single' | 'split') controls how many. setViewMode('split') keeps the existing first panel and adds a second one, defaulting to a different topic than the first so the two columns don't start out identical. setViewMode('single') just truncates the array back to one.

Everything that would otherwise be a single global ref becomes one of two things instead: a function that takes a panelIdx: number as its first argument, for anything that mutates a panel (loadIndicatorCards(panelIdx, topicName), selectIndicatorCard(panelIdx, indicator), handleMapLayerChange(panelIdx, layer)), or a function that takes a panel: ViewPanel object directly, for read-only helpers called straight from the template (getActiveCard(panel), getMapLookupRange(panel), getChipItems(panel)). The template then just runs v-for="(panel, idx) in panels" and every child element renders once per panel automatically. Single View and Split View are the same template, rendered against an array of length one or two.

Why this instead of Pinia?

With a store, two independent copies of the same feature usually mean either two separate store modules (duplicated logic) or one module keyed by an id (extra indirection for a fairly small app). Given there are only ever one or two panels, and nothing outside MainView.vue needs this state, a local ref<ViewPanel[]> plus plain functions is the simpler option, and this project's own guidance favors simple when simple is enough. If a third, genuinely independent page ever needs this same data, that's the moment to reach for Pinia instead.

09 Life of a click: choosing a topic

The clearest way to see how the pieces fit together is to trace one concrete action from start to finish: clicking "Schools" in a Split View column's Topic row.

  1. The click handler fires. The Topic pill's @click calls handlePanelTopicChange(idx, 'schools').
  2. The panel's topic and id update. panel.selectedTopic = 'schools'; panel.topicId++. That increment is what makes <MetricMap :key="...+ panel.topicId"> change, which forces Vue to tear down and recreate the map instance cleanly for the new topic instead of trying to patch it in place.
  3. loadPanelTopicData(idx) runs. This is the one per-panel pipeline function, and it does, roughly in parallel where it can:
    • loadIndicators() and loadTagCoverage(): what indicators exist for "schools", and which of them are attribute-completeness bars
    • loadIndicatorCards(idx, 'schools'): turns each indicator into a card, its display value, its gauge-ring percentage, its good/warn/bad/neutral level, and, through isNoQualityDescription(), whether it's a raw count like user-activity rather than a quality percentage
    • refreshActiveIndicator(idx, 'schools'): loads the map-coloring lookup and the small detail plot for whichever indicator ends up active
    • loadPanelTreemap(idx): the "Tag distribution" treemap for schools' grouping key, operator:type, or isced:level if that sub-toggle is on
    • updates schoolSwitchVisible so the operator/isced toggle only shows up for schools and hospitals
  4. Vue re-renders on its own. None of the above touches the DOM directly. Every one of those calls just assigns new values onto panel.* properties (or the ChipItem[] a computed helper derives from them), and Vue's reactivity re-renders whatever template expression reads them: the hero band's headline number, the indicator chip row, the map's :lookup prop, the plot container.
  5. MetricMap.vue reacts to its own prop changes through watch(). A new topicId triggers updateMapData() (rebuild the colored layer, re-fit the map to bounds). A new lookup object patches each shape's feature-state without a full rebuild, unless it's a count-type indicator, whose color scale depends on the lookup's own min and max and has to rebuild regardless.
  6. Plotly draws the plot. loadActiveIndicatorPlot(idx) and loadPanelTreemap(idx) both end in a Plotly.react(containerId, fig.data, fig.layout, {...}) call against a uniquely-id'd <div> (active-indicator-plot-a, tag-treemap-b, and so on). Plotly.react, not Plotly.newPlot, runs everywhere, so re-rendering the same chart with new data updates it instead of tearing the whole thing down and rebuilding it.

Switching countries (loadCountry()) is the same idea, one level up. Re-derive the available layers and topics, reset every panel to a fresh default topic, and call loadPanelTopicData(idx) for each one.

10 Components reference

ReportHeader.vue

The top bar. Purely presentational: it owns no data of its own, only props and emits.

PropPurpose
selectedCountry, countriesDrives the country <select>. Emits update:selectedCountry.
selectedTopic, topics, showTopicSelectorThe Topic pill row, only shown in Single View and the legacy iframe-2col mode (Split View moves topic-picking into each column instead).
viewMode, showViewModeToggleThe Single View / Split View pill toggle. Emits update:viewMode.

MetricMap.vue

One MapLibre GL instance. It gets used three times in the codebase: once per Single/Split View panel, dynamically through v-for, and once more, statically, inside the legacy iframe-2col template. Rebuilding the colored layer is driven entirely by prop watchers, see the walkthrough in §9. Two more things worth knowing:

  • Count versus percentage coloring. isCountIndicator switches the fill-color logic from a fixed red/amber/green quality scale to a continuous blue gradient stretched to the current data's own min and max. A raw count like "4,077 active users" has no universal good/bad threshold the way a 0 to 100% score does.
  • Split View's synchronized pan and zoom. Each map emits a move event, but only for a genuine user gesture. The handler latches a flag on movestart, checking e.originalEvent (only set for real mouse, touch or wheel input, never for a programmatic fitBounds or easeTo), and holds it until moveend. That way a whole animated gesture, including inertial wheel-zoom, which fires many move events but only tags the first, gets treated as one unit. MainView.vue listens for this and calls the other panel's exposed setView() (through defineExpose), which applies the camera instantly with jumpTo under an isSyncingView guard, so the sync can never trigger itself.

IndicatorGaugeCard.vue & AttributeCompletenessCard.vue

Used only in Single View's indicator stack. Split View replaced this with the compact chip row described in §11, a deliberate difference, not an oversight. IndicatorGaugeCard shows one indicator as a gauge ring plus a description, or, for a count-type indicator, a plain number badge instead of a ring (a percentage ring would imply a graded score that a raw count doesn't have). AttributeCompletenessCard is the same shape but bundles a <select>, so one card can represent several attribute-completeness indicators, surface, maxspeed, name, switching which one shows without needing a separate card per attribute.

ReportFooter.vue

Static legal links (Contact, Privacy, Imprint) and the ohsome dashboard badge. No props, no state. Safe to edit freely.

11 The design system

Every color, font and shadow in the redesigned Normal-mode UI is a CSS custom property, defined once in src/assets/main.css and consumed with var(--token-name) everywhere else, mostly inside MainView.vue's own <style scoped> block, plus each component's own scoped styles. There's exactly one palette. No dark mode toggle exists in this app today.

TokenValueUsed for
--paper / --paper-raised#F3F3F3 / #FFFFFFPage background / card background
--ink / --ink-soft / --ink-faintnear-black / gray / lighter grayPrimary / secondary / caption text
--accent#2185D0Links, active pills, focus rings, matches HeiGIT's real ohsome-dashboard product on purpose, not an invented brand color
--brand#CA2334The logo mark only, never used for interactive UI

A legacy set of tokens still exists too

--font-sans, --color-bg, --color-card-bg and a few others near the top of main.css exist only so the untouched iframe-2col layout keeps rendering exactly as it always has (it uses the Archivo font, not Lato). If you're styling something in Normal mode, ignore these. If you're carefully touching the iframe-2col template, these are the tokens it actually reads.

A few visual patterns repeat across the whole redesigned UI, and it helps to know them by name.

The pill is a bordered, rounded button that turns solid --accent when active. It shows up for topic selection, the view-mode toggle, and layer switching, and it's defined slightly differently in a couple of separate scoped <style> blocks: ReportHeader.vue's .pill, MainView.vue's .topic-pills-row .pill. That's not really a choice, it's unavoidable: Vue's <style scoped> doesn't share CSS between components even when the class name matches. If a pill somewhere looks unstyled, this is almost always why. The component rendering it never defined its own copy of the rule.

The chip is Split View's compact indicator and attribute picker: a small dot colored by quality level, plus a label, no ring, no description text (that's kept for Single View, where there's room for it). Look at getChipItems(panel) and .chip / .chip-dot in MainView.vue.

CSS Subgrid handles Split View's row alignment. .view-columns--split > .view-column uses grid-template-rows: subgrid, so column A's "mainview" section and column B's "mainview" section always start at the same height and take up the same height (whichever one is taller sets it), with zero JavaScript height-measuring involved. It degrades gracefully too: browsers without subgrid support just fall back to independent flex stacking per column, slightly misaligned but never broken.

Tailwind: present, but mostly unused

Tailwind is installed and configured (tailwind.config.js, postcss.config.js), and its @tailwind directives sit at the top of main.css. In practice, almost none of the redesigned UI actually uses Tailwind utility classes. The design system above, hand-written CSS custom properties plus scoped <style> blocks, is what you'll be editing most of the time. Tailwind is effectively legacy plumbing at this point. Use its utility classes for something new if you want to, but don't expect much precedent for it in the existing code.

12 Build, deploy & hosting

Deployment is fully automated through .github/workflows/deploy.yml at the repository root, one level above this Vue project, since this repo also holds the separate Python pipeline: 

on:
  push:
    branches: [main]

jobs:
  build-and-deploy:
    steps:
      - checkout
      - cd oqapi-country-reports-vue && npm install && npm run build
      - deploy ./oqapi-country-reports-vue/dist to the gh-pages branch

In other words: every push to main rebuilds and redeploys the live site automatically, with no manual step and no staging environment. Test locally before merging to main. There's no safety net after that point besides GitHub Pages' own rollback, which just means redeploying an older commit by hand.

The built app is served at https://<org>.github.io/osm-quality-country-reports/, note the sub-path. That's why vite.config.ts/.js hardcode base: '/osm-quality-country-reports/' as the default, overridden to / only for local dev through the VITE_BASE_URL env var in the dev script. If this app ever moves to a different host or a custom domain, this base path is the first thing to change. Get it wrong and every asset URL in the built dist/ output 404s.

13 Recipes: common changes

Concrete steps for the changes you're most likely to want to make.

Fix the duplicate Vite config problem
  1. Delete vite.config.js and vite.config.d.ts.
  2. In tsconfig.json, remove the "references": [{ "path": "./tsconfig.node.json" }] line. That's what caused vite.config.ts to get compiled into .js in the first place, through vue-tsc -b's project-reference build.
  3. Delete tsconfig.node.json itself, now unused.
  4. Run npm run build once to confirm nothing else depended on it, then run npm run dev and confirm the app still starts.
Restore the real country list
  1. Confirm the underlying S3 bucket-policy 403 on the ListBucket call is actually fixed. Ask whoever owns HeiGIT's storage infrastructure; that part is outside this repo.
  2. In onMounted() in MainView.vue, delete the hardcoded countries.value = [{ value: 'DEU', label: 'Germany' }]; selectedCountry.value = 'DEU'; block.
  3. Uncomment the real block right below it, the one calling fetchAvailableCountries(), and check whether 'RWA' is still the right default country or pick a different one.
  4. Test with a country other than Germany. It's also the only way to notice whether Germany's special-cased BKG layer names in getCountryLayers() have quietly leaked into code paths that were supposed to be country-agnostic.
Change the map's quality color scale
  1. The colors live in two places that have to stay in sync: buildFillColorExpression() in MetricMap.vue (the actual MapLibre paint expression) and every .map-legend block in MainView.vue's template (the on-screen key, currently hardcoded inline as style="background:#F44336" and so on, once per map instance).
  2. The three quality-band colors also exist as design tokens, --good / --warn / --bad in main.css, used by the indicator gauge rings and chip dots. Change the map's colors without changing these too, and the map will visibly disagree with the cards describing the same data.
Add a brand-new topic-specific config (like schools/hospitals have)
  1. Add an entry to topicConfig in helpers.ts if the legacy iframe-2col mode needs to know this topic's default comparison and completeness indicators.
  2. If the new topic needs its own tag-distribution grouping key, add a branch to getTagGroupingKey() in the same file.
  3. Normal mode mostly doesn't need topic-specific code at all. loadIndicatorCards and getChipItems already work generically off whatever indicators the parquet file actually contains for that topic. Special-case only genuinely special behavior, like the schools/hospitals operator-type / isced-level sub-toggle. Search for schoolSwitchVisible to see everywhere that toggle reaches.
Add a second real page/route
  1. Create a new file under src/views/, say AboutView.vue.
  2. In src/main.ts, add a second entry to the routes array passed to createRouter(): { path: '/about', component: AboutView }.
  3. Nothing else needs to change. App.vue's <router-view /> already renders whatever route matches.
  4. GitHub Pages serves this as a static site with one entry point, so a hard refresh on /about directly can 404 without an SPA-fallback trick (a duplicated 404.html). Worth testing once real deep-linkable routes exist.

14 Known rough edges

A punch list, in one place. Nothing here is broken today, but all of it is worth knowing before you assume the surrounding code behaves normally.

  • Two Vite config files, wrong one active. §2 and the first recipe above.
  • Country list hardcoded to Germany. §2 and the second recipe above.
  • No automated tests of any kind. Type-checking (vue-tsc) is the only automated gate; manual browser verification is mandatory for every change.
  • No ESLint or Prettier configuration. Code style is whatever the existing file already looks like. Match it by hand.
  • Two UI modes sharing one file. §6. Easy to edit the wrong branch, or to couple them by accident.
  • MainView.vue is a single ~2,600-line file. There's no enforced component boundary between map controls, the hero band, indicator picking, and so on. If this file keeps growing, pulling some of that out into dedicated components, the way MetricMap.vue and the two indicator card components already are, is a reasonable next step.
  • Tailwind is installed but mostly dead weight. §11. Not harmful, just don't expect to find conventions for using it.

15 Glossary

Topic
A category of OSM features this app reports on: roads, buildings, land cover, schools, hospitals. Each topic has its own set of relevant indicators.
Indicator
One specific quality metric within a topic, currentness, mapping-saturation, attribute-completeness_surface, and so on. Computed upstream by the ohsome-quality-api pipeline, not by this app.
Layer / grid layer
The geographic granularity a map currently shows: a whole country (adm0), a state or region (adm1), or a hexagonal grid (h3). Chosen per panel through the "Layer" pill row.
Grouping key / grouping tag
The OSM tag a topic's "Tag distribution" treemap breaks down by: highway for roads, building for buildings, operator:type for schools/hospitals by default.
PMTiles
A single-file vector-tile format that supports HTTP range requests, so a map can be served from one static file with no tile server. See §7.
Parquet
A compact, columnar binary file format for tabular data. This app treats every parquet file as a small queryable database through DuckDB-WASM, instead of parsing it into JSON up front.
DuckDB-WASM
A full SQL database engine compiled to WebAssembly, running entirely in the visitor's browser inside a Web Worker. It lets this app run real SQL queries against remote parquet files with no server-side query API. See §7.
ohsome-quality-api / ohsome-api
HeiGIT's separate backend services, not part of this repository, that the Dagster pipeline calls to actually compute quality indicators from OpenStreetMap history data. This app only ever reads their pre-computed output files from S3.
Panel
One independent map, topic and indicator combination in Normal mode. See ViewPanel, §8. Single View has one; Split View has two.
Single View / Split View
The two Normal-mode layouts, toggled in the header: one column, or two independent side-by-side columns.
iframe-2col
The legacy layout used when this app is embedded in an <iframe> by HeiGIT's HDX platform. See §6.
Hero band
The large "Medium 72%"-style headline box at the top of each panel, summarizing whichever indicator is currently active.

16 Where to go from here

Suggested reading order if you're starting from zero, in one sitting:

  1. Read this whole document once, top to bottom, without touching code.
  2. npm run dev the app and click through Single View and Split View for a few minutes, watching the Network tab to see the pmtiles and parquet requests happen live.
  3. Open src/views/MainView.vue side by side with §6 through §9 of this guide and trace one topic switch by hand, matching what you read here to the actual lines.
  4. Check whatever project instructions live in CLAUDE.md at the repo root for house rules on how changes should be made (small, surgical, verified in a real browser). Those apply to this project just as much as to any AI assistant working on it.
  5. Pick one item from §14 and fix it, as practice, before attempting a real feature.

This document describes the codebase as of the redesign that introduced Single View, Split View, and the CSS-subgrid row alignment. It will drift out of date as the app keeps changing. Treat it as a map of the territory on the day it was written, not a promise about the future. When in doubt, the source code is the final authority. This guide's only job is to make that source code fast to understand.
